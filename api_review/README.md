# 公開側の継続API処理

公開承認済みの公式資料の可視抜粋だけを処理する。非表示内容・個人情報・私的台帳は入力として公開しない。
2026-11-06の利用者指示により、新しいAPI結果は暗号化せず、version=2 / format=public-jsonで保存する。
結果は未確認の候補であり、fact_confirmed=false / publication_approved=falseを維持する。
公開候補には誤りがあり得る。本番記事の承認とは別であり、出典・引用・原本・表示を確認してから掲載する。
処理状態・件数・使用量は従来から平文であり、新方式でも公開する。APIキー・認証情報は公開しない。

## 稼働と重複防止

既存Secret OPENAI_API_KEYとVariable PUBLIC_API_ENABLED=trueを使う。新しい結果にAPI_RESULT_KEYは不要。
6時間scheduleとキュー更新pushはBatch APIへ最大100要求（最大300資料）を一括投入し、即終了する。
API側のcompletion_windowは24h。次の定期実行で状態を1回だけ確認し、完了結果を回収する。
待機ループやsleepはなく、APIの処理時間中にActions runnerを占有しない。
PR時だけ固定応答テストを実行し、定期実行では再実行しない。checkoutもAPI関連に限定する。
document-onceは既存の同期1要求に限定したまま。1要求3資料/16KB/出力1200tokens、
送信前CAS予約、concurrency、原本SHA+本文の重複防止を維持する。失敗・中断・保存不明は自動再送しない。
APIはstore:false。空キューは待機せず終了する。課金・予算・原本収集・本番公開の設定は変更しない。

正本はapi-public-stateブランチのapi-runtime/ledger.json。既存台帳を空にして初期化しない。
api_review/queue.jsonには公開再配布を確認した抜粋をPRで追加する。
公開入力とAPIの下書き候補が公開repoで閲覧可能になることを確認する。
非公開側へ移管する場合は従来どおり委任台帳・原本SHA・本文・要求IDを照合し、二重投入しない。
公式資料の収集・公開承認・記事掲載は既存工程で行う。承認済み在庫の補充は下記のsupply経路を使う。

## 旧暗号化結果の復旧

API_RESULT_KEYは旧version=1結果の復旧にだけ任意使用する。新しい結果の必須条件ではない。
公開側の既存鍵で、現行承認キューと要求ID・出典・引用・状態・使用量が一致した旧結果だけを、
APIへ再送せずversion=2へ変換する。旧暗号文はlegacy_encrypted_reportに保持する。
鍵がない/読めない/一致しない旧結果はlegacy_heldに明記し、新規の独立資料を止めない。
既存結果・失敗・予約を消したりIDを変えて再送したりしない。

## 受信

サイト側は固定の公式GitHub HTTPS endpointから読み、委任要求・本文SHA・出典・引用・状態・使用量を再検証する。
version=2のSHAは転送破損の検出用であり、署名ではない。取得元と私的な委任台帳の照合を省かない。
新しい結果は鍵なしで受信できる。旧暗号化結果は鍵不在/不一致なら保留件数に示し、平文結果の取り込みを続ける。
api_review/receive.pyもversion=2を鍵なしで読み取れる。受信を本番公開承認とは扱わない。
非公開repoの資格情報を公開側へ渡さない。ログへAPIキーや結果本文を出さない。

## 限定検証

python -m unittest discover -s api_review -p 'test_*.py'
PRでは固定応答テストのみ。無関係な全体CI、原本の再取得、APIの再送は行わない。
key-checkは旧来の一度限りの診断経路として保持し、通常の新方式の稼働条件にはしない。

## Batchの運用と残る供給工程

同期workerと同じpayload SHA/原本SHA＋本文キーを使い、過去の完了・保留・予約を再送しない。
送信前CAS予約→ファイル投入→Batch ID保存→後続runで回収。送信結果が不明な場合は予約を残し自動再送しない。
Batch失敗/期限切れ/部分失敗も結果と使用量を保存し、完了していない範囲を成功扱いにしない。
新規結果は従来と同じpublic-jsonで、根拠引用の検証と公開承認falseを維持する。
API残高の自動取得や無料枠超過の自動課金許可を追加していない。追加購入・自動チャージを変更しない。

出力検証失敗はledgerの要求レコードに固定のdiagnosticを保存する。未完了応答、明示された
出力上限、JSON/項目形式、引用形式/不一致、根拠なしverify、非verifyの原稿を区別する。
未検証の本文・例外文は保存/ログ出力しない。report形式・payload・判定基準・送信予約は維持し、
診断追加前の失敗理由は推測で補完しない。理由コードは再送許可や公開承認ではない。

Batchは資料を自動収集しない。公開キューが既処理1件だけなら新規送信0件になる。
継続供給には保存済み未処理資料の公開可視範囲を確認し、私的キューとの二重委任を防ぎ、
元の出典/SHA/本文/要求IDを保持して公開キューへ補充する必要がある。
未確認の原本・非表示内容・私的台帳を一括公開して件数を増やさない。
稼働確認では投入数/処理中/回収完了/検証保留/実tokenを別々に数える。

公式仕様: https://developers.openai.com/api/docs/guides/batch


## 承認済み在庫からの自動補充

既存の6時間scheduleで、batch_workerはsupply.jsonを読み、承認済みbundleをメモリ上のキューへ補充してから既存Batch処理を1回実行する。mainへの書込み、新規workflow、追加の定期タスク、待機、手動API送信は追加しない。queue.jsonの既存4要求は変更せず、送信済み3要求の結果回収にも同じ入力を使う。catalogの変更は次の自然scheduleで処理する。

supply.jsonは公開レビューを通した可視抜粋の在庫であり、収集先一覧ではない。未承認本文・原本・非表示情報・個人情報・非公開台帳をここへ移さない。未承認候補は従来の非公開収集台帳に保持する。公開可能な候補でも承認情報が不足すればsupply_confirmation_requiredとして件数のみ記録し送信しない。現在の在庫は空であり、新規資料の承認完了や無停止供給の達成を意味しない。

登録は既存の収集・検査・prepare/previewを担当する工程で行う。候補ごとにbundleとapprovalのみを登録する。approvalはbundle_sha256（worker.digestによる正規化JSONのSHA）、review_commit、documents、exclusive_public_ownershipを持つ。documentsはbundle順にid/source_url/original_url/source_sha256/text_sha256/terms_url/license/checked_at_jst/public_scope/visible_only/no_personal_information/redistribution_approvedを記録する。本文変更・原本更新・範囲変更は再レビューする。URLや利用条件の存在だけを公開承認とみなさない。

公開前に非公開側の全履歴（処理中・保留・完了・中断予約を含む）を原本SHAと本文/要求IDで照合する。既存の委任手順で対象を公開側専有として永続予約し、非公開キューをdelegated_to_publicにしてから、確認したprivate_state_commit、reserved=true、no_prior_attempt=trueだけを公開可能な承認記録として記載する。非公開台帳やrequest_pathは転記しない。既存履歴がある・照合不能・委任予約できない場合はこの承認を作成せず確認待ちにする。専有予約は公開側に保留や失敗が生じても解除しない。再試行は別途照合を要する。

公開workerは非公開資格情報を持たないため、この委任証跡の真偽を非公開側へ照会できない。review_commitとprivate_state_commitは署名ではなく、レビュー時に確認した固定版の参照である。担当工程で実照合・予約を完了することが必須であり、推測でtrueを設定しない。自動収集した新規原本を自動承認する機能は追加しない。

同一原本SHAまたはbundle IDは在庫/既存キュー内で重複補充しない。API送信自体は従来のpayload/source_keysと永続CAS予約で全状態に対して再送を防ぐ。queue.jsonと承認済みcatalogは回収・履歴照合用に保持し、処理済みだからという理由で削除しない。上限1000要求に達した場合は確認待ちとして運用整理し、履歴を消さない。

確認した既存のworkloads/collectors.pyは施設基準・食品営業の取得/正規化で、API公開承認の代替にならない。既存のPR/CI監視タスクにも補充指示があるため、同工程はsupply.jsonへのレビュー済み登録に集約し、同じ資料をqueue.jsonへ重複追加したり手動送信したりしない。既存スケジュール・購入・自動チャージは変更しない。


## 一次検査の自動完結（2026-11-07 方針変更）

新規API要求はid / assessment / evidence / rationale / next_checkの5項目だけを返す。
一次検査に記事・X原稿の生成を混ぜない。理由と次確認は各100字以内、出力上限は1200のまま。
検証後は既存7項目の受信形式へ正規化し、原本SHA・引用・公開承認falseを保持する。
旧7項目の処理中応答も回収可能。プロンプト変更による要求ID変更で過去の資料を再送しない。

- reject：公開可視抜粋に明白な指摘なしとして処理完了。原稿は作らず、Workで同じ範囲を再検査しない。資料全体の正確性を保証する意味ではない。
- hold：根拠不足として保存。問題なしと区別し、自動再送・Workによる大量代行はしない。追加根拠が必要な案件として残す。
- verify：原文引用の厳格検証後だけ、資料名・短い理由・最初の引用から定型下書きを自動作成。全引用はevidenceに保持する。追加のモデル要求は行わない。Workはこの候補の公開前確認に絞る。
- invalid_output：固定診断を保存して保留。失敗のたびに同じ診断や修正を繰り返さず、新しい診断・影響のある不具合に限定して対応する。

回収ログには資料数でtriage_no_finding / triage_needs_evidence / triage_candidatesを出す。
completed/heldは従来どおり要求の処理成否であり、意味上のhold件数と混同しない。
通常監視はこの差分集計と新しい診断を先に確認し、問題なしの本文をWorkへ再投入しない。
原本の収集・公開入力の承認・本番掲載承認は別工程。定型下書きは公開済み記事ではない。

API専用固定応答テスト52件成功。実モデルの成功率とWork消費削減は次の自然定期実行以降に評価する。
