# API資料検査の優先配分

## 通常運用

既存の自然Batch実行を継続する。手動投入・課金設定変更・新規workflowは行わない。
補充数を新規送信数と扱わず、公開台帳を正本として状態を確認する。

1. 回収済みverify候補の原本・注記を確認する。同じ入力をAPIへ再送しない。
2. batch_submittedの結果を既存定期実行で回収する。予約・中断・保留も重複除外に残す。
3. 未送信の承認済み資料がある場合のみ、新しい内容と具体的影響が期待できる資料を優先する。
4. 今後の承認工程では、条件・期限・注記と本文の照合が可能な独立資料を優先する。
   同じ形式の人口表の合計照合など機械で判定できる項目は先にオフラインで確認し、
   異常や解釈を要する箇所をAPI候補とする。これは未承認資料の投入許可ではない。

完了したrejectの同一範囲をWorkで再検査しない。出力検証失敗は問題なしと区別し、
原因の推測・ID変更・形式変更だけで再送しない。原本SHA、本文、公開側と非公開側の全履歴を照合する。

## 読み取り集計

既存の承認キュー・在庫と、取得済み公開台帳を用いて次を実行する。

```sh
python api_review/metrics.py /path/to/downloaded-ledger.json
```

API呼出し・台帳書込みはない。inventoryは要求単位で未処理・処理中/予約・完了・保留を区別する。
過去payloadが異なっていても同じsource_keysがあれば再送対象にしない。
候補率は検証通過した資料のverify比率であり、原本確認済み率や公開成功率ではない。
usageは記録されたトークンだけで、請求全体やクレジット残高ではない。
成功要求あたり平均は使用量が記録された成功要求のみで計算する。
残高・正確な失効時刻を取得できなければ未確認とする。
